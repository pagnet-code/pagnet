# Private owner content

A personal representative can run without joining a network. Its private native permission details use an `account_host` protected content context, not a hidden network. The context binds its ID, organization, account owner and host. Network memberships and delegated or selected-network credentials grant no access to this context. The control plane enforces account authentication and ownership; encryption keeps the protected contents and keys out of its database and normal relay processing.

The owning runtime process generates and retains context epochs under its private Pagnet state directory, `e2ee/contexts/<context-id>/keyring.json`. Its public identity is recorded with the exact runner connection generation. Other processes reporting inventory on the same host cannot replace that identity. Preparation is a durable, signed command outcome committed atomically with readiness; it does not stop or restart native work. Existing pending details can be enriched only from the same native observation retained locally. Already discarded details cannot be reconstructed from server metadata.

Browser key sessions last fifteen minutes, with at most 64 sessions and 32 stored objects per unwrap request. Each object is limited to 64 KiB and authenticated with its complete context, object and epoch AAD before its content key is wrapped to the browser's X25519 key. Existing network AAD canonical bytes remain unchanged. Pending native observations are bounded to 64 and retained for the durable permission lifetime of 24 hours, or until native resolution; they are never uploaded as plaintext.

Allowing a permission requires explicit inspection. A secret delivered inside the encrypted detail authenticates the exact AAD, instance, native session, native request generation and selected option. The host verifies that proof against its retained observation and the still-pending native request. Rotation cannot intervene between verification and native delivery. Rejecting a known native rejection option does not require inspection. HTTP acceptance records a pending command; only the originating runner generation's native confirmation resolves the permission. A runtime without a supported native permission API cannot be made remotely approvable by typing arbitrary commands.

Owner-authorized `POST /api/v1/protected-contexts/<id>/rotate` accepts `{ "instanceId": "<owned-instance-id>" }`. It rotates the local epoch and invalidates browser sessions while preserving native work. Old non-revoked epochs remain available for protected historical objects; old inspection proofs cannot approve a newly protected observation. A failed preparation is reported as failed, never retried by background reads. After checking the same host and restoring its local keys when necessary, an owner can explicitly call `POST /api/v1/protected-contexts/<id>/retry` with the same instance body. Retry preserves the context and expected epoch. Lost or revoked keys are not silently replaced, and this operation does not promise recovery of unreadable historical content.

This feature requires a host advertising `owner-context-v1` with its actual public keys. Older hosts report unsupported; disconnected or replaced observation generations report offline. Interactive terminal traffic retains its documented TLS/WSS relay boundary and is not covered by owner-content encryption. Windows owner-context storage is currently unavailable.

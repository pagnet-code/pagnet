# Managed project v1 implementation RFC

Status: **proposed, unshipped; activation disabled**. This RFC specifies `managed_project_v1`; it does not implement an API, change current eligibility, or authorize deployment. Existing `sdk_project_v2` remains a service-only contract. The [cross-account sharing design](CROSS_ACCOUNT_SHARING.md) supplies the wider context; this RFC narrows the first managed-agent increment.

## Contract and authority

A project has exactly two distinct personal human owners in their respective personal tenants. Each owner selects 1–4 of their own managed agents, for a total of 2–8. Organizations, third owners, dynamically added participants, arbitrary services and unselected agents are ineligible. Both owners consent to the exact roster, agent-to-adapter bindings, execution-profile commitments, expiry and six aggregate limits before enrollment. Selection proves current ownership server-side; a supplied name, principal ID or host ID is never authority.

Each selected managed agent receives a dedicated owner-owned service principal with `principal_mode = managed_project_adapter`, unique to `(projectId, managedPrincipalId)`. Its owner and tenant equal the managed agent's. It is distinct from standard SDK services eligible for `sdk_project_v2`; neither mode can enroll in the other's transport. An adapter has only project enrollment, roster-scoped encrypted ASK/REPLY, receipts and acknowledgement rights. It cannot use generic service credentials to join networks or call managed launch, task, invocation, artifact, host or account APIs. Provisioning must issue a restricted adapter credential, never an owner's general credential. Reusing an adapter across projects is forbidden.

The foreign managed agent gets **no ordinary network membership**. A dedicated transport scope ID may reuse the v2 network-ID storage primitive, but must not create normal memberships, distribute either home network's epoch keys, or make generic network routes authorize traffic. The transport admits only the fixed adapter roster. Its discovery response contains project-selected display names and identities, never home-network inventory, host paths or other agents. Project messages grant communication, not actions or host control.

Roster, bindings and profile commitments are immutable after proposal creation. An owner cannot swap an agent, host, adapter identity/key or profile under an accepted name. Changes require a new project, fresh bilateral consent and enrollment; no inherited history or retry IDs. Display labels may change without changing authority, with UI freshness explicit. Expiry and limits are committed too; v1 replaces the project to change them. Either owner may revoke immediately without peer consent.

## Proposed durable schema

These are new logical records and constraints, not an assertion that current tables support them. Use the repository's UUID, canonical descriptor and SHA-256 conventions; pin canonical encoding and fixtures before implementation.

| Record | Required fields and invariants |
| --- | --- |
| `managed_project` | `id`, `contract = managed_project_v1`, isolated `transportScopeId`, two `(userId, tenantId)` owners, `name`, `expiresAt`, six limits, `policyHash`, immutable canonical commitment bytes/hash, `state`, monotonic `revocationVersion`, timestamps and unique owner-scoped creation `requestId` plus request digest. |
| `managed_project_binding` | `projectId`, owner/tenant IDs, `managedPrincipalId`, dedicated `adapterPrincipalId`, `principalMode = managed_project_adapter`, adapter public key, exact `hostId`, `executionProfileId`, immutable `executionProfileRevision` and `executionProfileDigest`, `deliveryMode = running_only`, `sessionScope = project_isolated`. Unique agent and adapter per project; adapters globally bind to only one project/agent. |
| `managed_project_consent` | Owner ID, accepted commitment hash, expected project/revocation version, timestamp and authenticated actor. Both records must reference the same immutable bytes. Proposal creation records issuer consent; recipient acceptance supplies only their own consent. |
| `managed_project_enrollment` | Project, adapter, endpoint/credential binding and generation, descriptor hash, pinned key, expiring HPKE challenge/proof, proof state. All selected adapters independently pin and prove the same descriptor; an owner click cannot substitute for endpoint proof. |
| `managed_project_delivery` | Existing v2 logical message/reservation/receipt fields plus project commitment, sender/recipient binding IDs, consent/revocation version at admission, deadline, host adapter delivery state, session activation generation and durable local delivery ID/digest. No plaintext in server quota/audit records. |
| Host-local binding | Verified commitment/descriptor hashes, local profile digest, exact managed identity/host, project-scoped session identity and activation generation, restricted adapter key reference, durable dedupe/outbox/inbox state and revocation watermark. Private files use existing private-state protections. |

Create the proposal only after both owners' selected bindings and public profile commitments are known. The recipient's owner-authenticated UI can supply their candidate selection through a preparatory draft exchange; draft metadata is not consent, enrollment or delivery authority. A final proposal freezes both sides and issuer consent. Reject partial/duplicate rosters, third owners, wrong ownership/mode, reused adapters, expired profiles and ownership races atomically. A concurrent binding change must fail proposal finalization, not silently select a replacement.

The canonical policy commitment includes the contract, project/scope IDs, ordered owner identities, ordered managed/adapter bindings and public keys, profile IDs/revisions/digests, running-only/session-isolation modes, permissions (`communicate` only), expiry and all limits. The enrollment descriptor additionally binds the agreed policy hash and cryptographic suite. Public profile commitments expose policy identity, not provider credentials, executable arguments, private paths or secrets. Descriptors are pinned before proof; first-contact server directory trust remains explicit, with optional independent fingerprint comparison as in v2.

States are `proposed`, `accepted_pending_enrollment`, `active`, `revoked` and `expired`. `active` requires both consent records and every adapter's proof; it means transport enrollment, not runtime readiness. Readiness is an on-demand snapshot with a timestamp and per-binding blocked reason. A disconnected host, missing session or profile mismatch makes that binding non-deliverable immediately. Revoked/expired projects never reactivate; replacement uses a new ID.

## Proposed API surface

All paths below are proposed under `/api/v1`, separate from `/sharing-project-transports`. Owner routes authenticate a human owner; adapter routes authenticate the exact restricted endpoint credential. Server authorization rechecks contract, ownership and binding on every route. Unknown fields/modes must fail closed. Do not add a managed-principal exception to existing v2 checks.

| Route | Contract |
| --- | --- |
| `GET /managed-project-candidates` | Owner-only name picker for their eligible managed agents and local profile commitment/readiness summary. No foreign inventory. |
| `POST /managed-project-drafts` and owner-scoped draft selection | Exchange only the two owners' explicit candidate selections; finite expiry and rate/body caps. Cannot enroll, send or execute. |
| `POST /managed-projects` | Finalize exact draft revision with `requestId`, canonical commitment hash and both selections. Validate all bindings; atomically create project and issuer consent. Identical retry returns the same result; conflicting digest fails. |
| `GET /managed-projects` and `GET /managed-projects/{id}` | Owner's projects and exact consent review. Only named owners can read; names confer no authorization. |
| `POST /managed-projects/{id}/accept` | Recipient owner accepts `expectedVersion` and `commitmentHash`; stale/mismatched consent fails. No keys or messages until full enrollment. |
| `POST /managed-projects/{id}/revoke` | Either owner supplies `expectedVersion`; transaction advances the durable fence, closes admission and emits invalidation. Idempotent repeat reports terminal state. |
| `GET /managed-projects/{id}/readiness` and `/usage` | On-demand owner snapshots, timestamped; v2-compatible six-limit units, windows, reset times, reservations and lifetime totals. No periodic idle polling. |
| `GET /managed-project-transports` and `/{id}/status` | Exact authenticated adapter's projects/status and selected roster only. No enumeration through guessed IDs. |
| `POST /managed-project-transports/{id}/pin`, `/challenge`, `/prove` | Reuse v2 enrollment sequencing and endpoint-bound proof with the new descriptor/domain. Retries cannot prove another credential or generation. |
| `POST /managed-project-transports/{id}/messages` | Canonical encrypted ASK/REPLY only; same aggregate durable v2 admission and retry rules, plus current managed binding/consent fences. |
| Inbox, acknowledgement and receipt routes under that transport | Mirror v2 encrypted transport recovery semantics; only the exact recipient/sender may access appropriate records. Authenticated sender receipt lookup remains available for retained historical message IDs after expiry or revocation so ambiguous sends can settle, but it grants no new send, fetch or execution authority. |
| `POST /managed-project-transports/{id}/messages/{messageId}/authorize-start` | Restricted to the bound owner host and adapter incarnation. In one transaction, lock and recheck both consents, revocation version, expiry, exact binding/profile/descriptor, credential generation, running session generation, message digest and local execution reservation; issue a one-use permit bound to all of them with at most five seconds' validity. An identical retry returns that permit only while still live and unconsumed, otherwise its recorded terminal status; changed inputs fail. No permit is issued offline or after revocation. |
| `POST /managed-project-transports/{id}/messages/{messageId}/runtime-outcome` | Bound host reports accepted, started, completed or terminal failed/cancelled execution with durable idempotency; this is separate from encrypted transport ACK and cannot turn a receipt into execution authority. |

An owner command to start a local project session is separate from this transport. The peer and adapter have no launch/wake endpoint. UI hides unavailable actions, but server and host checks enforce this independently.

## Encryption, budgets and recovery

Reuse the existing v2 AuthHPKE suite `HPKE-X25519-HKDF-SHA256-AES256GCM-Auth-v1`, independent per-adapter key enrollment, immutable prepared bytes, scoped durable idempotency, reservation/receipt lifecycle, expiry, bounded retries and reconnect recovery. The [v2 enrollment](../sdk/sharing_project_enrollment.go), [message format](../sdk/sharing_project_messages.go) and [durable spool](../sdk/sharing_project_message_spool.go) are implementation references, not managed-project eligibility today.

Use new domain separation: message HPKE info `pagnet/managed-project/message/v1`, proof domain `pagnet/managed-project/proof/v1`, and a canonical message AAD header with explicit `domain = pagnet/managed-project/aad/v1` and `contract = managed_project_v1`. Bind project/scope IDs, policy/descriptor/commitment hashes, sender and recipient adapter IDs and binding IDs, message/thread/correlation IDs, kind and creation timestamp. Canonical field order and encoding are a versioned contract. Proof AAD additionally binds adapter, endpoint, credential/generation, challenge and descriptor hash. Reject v2 envelopes, swapped bindings/profiles, altered domains and cross-project replay even if keys or IDs are supplied incorrectly. The immutable committed profile is transitively bound by its commitment hash; changing a local policy cannot preserve readiness under that hash.

Reuse exactly the six project-aggregate v2 limits: `maxMessageWireBytes`, `maxMessagesPerMinute`, `maxMessagesPerDay`, `maxWireBytesPerDay`, `maxInFlight`, `maxTurnsPerThread`. They include replies and traffic from all adapters, never reset per agent or reconnect, and count canonical encrypted wire bytes rather than model tokens or monetary spend. Admission, reservation and queue write remain atomic. Identical ID/bytes return the recorded result without a second logical charge; conflicting bytes fail. Ambiguous sends recover from durable prepared messages and receipts, not a new ID. Preserve existing correlation validation and terminal transport-reservation reconciliation. Transport ACK releases the transport in-flight reservation only after durable receiver storage; it does not assert model execution. A separate finite host execution queue and budget prevent acknowledged messages from accumulating without bound. Host execution time, tools and provider cost need separate finite profile controls; relay quotas do not supply those controls.

## Host adapter and project-isolated session

### Owner execution requirements and enforcement evidence

`runtime_profiles` currently reports availability, not a security boundary. Before project consent is implemented, add an immutable `managed_execution_profile_revisions` record for each selected agent and owner host. The owner approves a fixed, versioned policy template with typed finite limits and resource references; the server builds canonical policy bytes and SHA-256 from authoritative fields. The record binds owner, agent, host, revision, approval and expiry. Replacement creates a new revision and atomically revokes its predecessor; revocation is append-only. Consent later binds the exact revision ID **and** hash and never follows a successor automatically. Creating a record grants no network membership, launch, project admission or execution authority. Its status is **requirements saved, enforcement unverified**.

The template requires a fresh project workspace and native state, default-deny files/network/IPC, only explicit runtime support and project broker resources, a cleared environment with scoped credentials, a project-only tool set, inherited descendant containment, and finite time, concurrency and usage limits. It must not contain secret values or trust arbitrary owner-supplied paths and policy hashes. A host compiler may resolve local paths only under the bound owner host's authority. The ordinary runtime sandbox spec, which permits native auth/session state and coarse support paths, is not automatically a valid project profile.

Later enforcement evidence must bind a server challenge, current authenticated host connection, exact revision/hash, project/run/session generation, runtime and sandbox compiler versions, compiled policy digest, installation result and finite lease. A host signature proves the registered host reported those facts; it does not independently prove kernel containment. The server accepts only supported host software and tested platform/runtime combinations. No current host report or `runtime_profiles.available` result can satisfy this gate. A failed, stale, unverifiable or unsupported profile keeps the project inbox quarantined.

The host receives a binding only for its owner's exact managed principal and host, verifies the committed descriptor/profile, and keeps adapter credentials outside the runtime. The trusted host adapter terminates project encryption and deliberately passes the admitted plaintext into a project-only runtime context. It can read that plaintext and is part of the confidentiality boundary; encryption does not protect against the owner, adapter, runtime/provider or intentional plaintext release.

`running_only` means an already-running, owner-started **project-isolated session** for this project and selected agent. A running private/home-network session is ineligible. Use separate conversation history, native session identity, memory, workspace/data grants and tool surface; no private transcript, home-network keys, global memory, owner inbox or other project context is injected. Selecting an agent selects its identity and explicit project profile, not all its private knowledge. If a runtime cannot prove this separation, readiness is blocked. Do not route through a shared PTY, type foreign text into a private terminal, or fall back to an arbitrary live session.

Before each delivery, the host checks live owner/agent ownership, both consents, expiry/revocation watermark, exact adapter binding and activation generation, current independently verified execution profile and remaining local controls. A runtime profile in [RUNTIME_PROFILES.md](RUNTIME_PROFILES.md) selects executable/provider configuration; it is **not** proof of an enforced owner-execution security profile. The latter must constrain filesystem/workspace and native configuration access, tools/bridge routes, memory, destinations, child processes, elapsed time/concurrency and credential exposure, with a verified enforcement result tied to the running process tree and policy digest. [Process binding](BRIDGE_PROCESS_BINDING.md) authenticates a process; it does not supply these restrictions.

The adapter submits only scoped message content and authenticated origin/correlation metadata through the structured session interface, with a finite causal budget. Every runtime-originated follow-up and descendant action inherits the original authenticated causal root and its remaining turns, calls and execution budget, even if it creates a new message or thread ID or reconnects. The host persists and enforces this root; the runtime cannot mint a fresh root for foreign-triggered work. It cannot forward generic network/task/invocation operations. The runtime can reply only through this adapter's scoped route and immutable binding. Descendants inherit the same restrictions. No foreign payload may select executable, shell, workspace, native session, tools, policy, keys, launch or wake. Missing/unsupported enforcement quarantines delivery for owner inspection; owner-readable inbox content remains untrusted and inspection does not execute or launch anything.

Persist admission and local delivery state before submission. Recover unknown runtime outcomes conservatively; do not automatically resubmit a possibly executed turn unless the runtime supports durable submission dedupe/status for the same delivery ID. Transport dedupe alone cannot promise exactly-once runtime effects. Keep transport receipt state (`pending`/`acknowledged`) separate from host runtime state (`quarantined`/`authorized`/`started`/`completed`/`terminal_failed`/`cancelled`). Reconcile transport and execution reservations independently; runtime failure cannot fabricate a reply or erase a retained sender receipt.

## Stale queue and revocation fences

A server admission is not permanent permission to execute. Both the relay dequeue and host's final submission boundary revalidate current consent, expiry, binding and monotonic revocation version. Invalidation events accelerate fencing; event delivery alone is insufficient. Immediately before submission the host obtains the one-use `authorize-start` permit described above and consumes it under a local lock tied to the same delivery ID and session generation; offline, expired, changed or already consumed permits block submission. A restarted or reconnected adapter reconciles revocation and descriptor state before draining anything.

Serialize local revocation/stop processing with submission so a locally observed newer fence cannot be overtaken by an older queued item. Server revocation atomically blocks future permits and admissions. A permit issued before revocation may still be consumed before its five-second expiry if the host has not yet observed the new fence; classify that interval as **authorized but start uncertain**, distinct from work known to have started. Cancel it best effort and report the uncertainty rather than claiming that revocation stopped every subsequent local effect. On invalidation, stop further turns/tool effects as the verified profile permits, close new project operations while preserving retained authenticated sender receipts, cancel queued work, retire session generation and reconcile reservations exactly once. Never claim rollback of irreversible effects or erasure of retained plaintext/keys.

Queue items have finite deadlines and retained idempotency fences at least as long as supported queue/retry recovery. Revoked, expired, mismatched-profile and old-generation items become terminal or quarantined, never silently rebound to a replacement agent/project/session. A later owner-started session requires a fresh generation and fresh current authorization; it does not wake or revive stale work. Loss of live authorization keeps the inbox owner-readable but non-executable. Store audit IDs, hashes, state transitions and blocked reasons without prompts or results.

## Owner experience

Use a simple agent-name picker for each owner's 1–4 selections, with peer owner identity, selected agent names, expiry and finite usage preset in the bilateral review. Show a concise profile label and readiness reason; expose fingerprints, exact profile revision and limit units in details. Resolve duplicate display names with an owner-visible disambiguator. Draft selection is visibly pending and cannot imply acceptance.

Provide explicit on-demand Refresh, readiness and usage views, plus revoke. Do not require owners to manage SDK services, host paths or adapter keys. Readiness states such as “owner must start project session”, “host offline”, “profile verification blocked” and “revoked” describe the actual delivery gate. Never offer peer-triggered Start/Wake. Metadata disclosure includes participant names/IDs, timing, ciphertext sizes and usage; snapshots must not reveal private activity or credentials.

## Platform blockers and release gates

**macOS remains blocked for this contract.** PR #17's proposed Darwin Seatbelt policy is unenabled; its presence on a branch is not an activated or verified execution boundary. Qwen, PTY and full real-runtime macOS tests are pending. Process-binding, supervisor tests or cross-compilation do not close these gaps. Do not activate managed external delivery on current macOS `allow_all`/unsupported containment or infer support from a Seatbelt policy file. Require actual owner-profile enforcement and negative containment tests across each supported runtime, its native tools, descendants and terminal paths before enabling that combination.

**Linux support is conditional, not automatic.** Existing managed sandboxing requires detected Landlock ABI3+ (normally Linux 6.2+ with Landlock enabled) and must fail closed when unavailable. The current filesystem policy is not a complete project execution profile: pathname Unix socket connections are not constrained by it; device access retains OS permissions and IOCTL caveats; metadata visibility and allowed runtime/provider directories need review. Generic egress, native tools, credentials, memory and project context isolation need independent enforcement/testing. A kernel/version label or successful executable discovery is insufficient. Unsupported Linux profiles remain quarantined with no automatic runtime delivery.

Backend, client/host and web need compatible explicit `managed_project_v1` negotiation, durable schema/admission, mode-specific credential authorization and tested fences. Older clients must reject, never downgrade to v2 or ordinary network delivery. Activation stays disabled until the vertical acceptance proof below and platform/runtime negative tests pass. This RFC alone closes none of these release gates.

## Vertical acceptance test

Run a coordinated server + web + two real owner hosts + real runtimes test on each proposed supported platform/runtime/profile combination. Keep unsupported combinations blocked. Capture versions, policy digests, real enforcement evidence and metadata-only receipts; mocks alone do not pass.

1. Create two personal accounts with private agents, history and sentinel files. Each owner selects one named managed agent (then repeat cardinality checks at 1 and 4 each). Provision dedicated adapters; reject zero/five agents, third owner, wrong-owner agent, standard SDK service, reused adapter and ordinary network enrollment. Verify neither peer can list private inventory or obtain home epoch keys.
2. Finalize the exact commitment. Before recipient consent, sending, proof activation and runtime delivery fail. Accept the displayed hash, independently enroll all adapters and show active transport with runtime readiness still blocked. Mutate roster, binding, profile digest, credential generation or acceptance version and verify rejection. Existing v2 standard service flow still works; managed adapters cannot enter it.
3. Keep a private runtime running: an admitted project ASK must never enter it. With no project session, receive only quarantined/inbox state and no launch/wake. The local owner starts a separate project session with the exact verified profile. Refresh readiness; only a fresh authorized delivery may enter that session. Verify no private history/memory, sentinel access, forbidden tools/bridge routes, keys or other-project state is available, including through descendants and native terminal/tool paths.
4. Send encrypted ASK and correlated REPLY between selected agents. Validate origin, AAD and domain separation, v2 envelope rejection, non-roster routing denial, shared aggregate limits (including replies), exact wire accounting and authorized on-demand usage. Tamper each bound identity/hash/domain and replay across projects; all fail before runtime submission. Exhaust each of the six limits concurrently and verify durable bounded denial/backoff.
5. Drop a send response and restart server/adapter around admission, dequeue and runtime submission. Retry the same immutable bytes: one logical reservation/result, no duplicate known submission; conflicting digest fails. For an unknown runtime outcome, require durable runtime status/dedupe or quarantine instead of blind replay. Reconcile receipts and reservations after recovery.
6. Queue an ASK while offline; revoke from either owner, then reconnect. Also race revocation/expiry/profile drift and session restart with dequeue and final submission. Stale items must not enter a runtime, launch/wake, switch generations or restore participation. Verify server fences and local current-authority checks when invalidation events are dropped. Record any already-begun effects honestly and prevent subsequent effects where supported.
7. Reopen web views: only accepted names, permitted readiness/usage metadata and concrete blocked reasons appear. Audit/quota logs contain no protected payloads. Verify no project lifecycle creates foreign ordinary membership or generic host/task/invocation authority. Repeat against stale clients and unsupported profiles: activation/delivery fails closed with no fallback.

Acceptance requires both owners' revocation tests, multi-adapter aggregate/race tests, real project-context isolation and the platform gates above. Missing macOS runtime evidence and Linux profile gaps remain explicit blockers, not follow-up work after activation.
